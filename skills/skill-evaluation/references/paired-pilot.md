# A small paired pilot

Use this when a method change needs initial evidence, not when correcting an
already justified typo. Reuse the available client, existing evaluation packets
and ordinary artifact inspection. This is not a requirement to build a runner,
dashboard, sandbox, exporter or new results database.

## Fix the question before the runs

Choose whether the comparison is previous bytes versus candidate, or the same
task without versus with the skill. Do not switch the baseline after seeing an
unfavorable result. Record skill/input identity, model and client configuration,
tools, permissions, context and invocation route in the existing evidence record.
Keep the requested outcome and acceptance independent of the candidate's answer.

Start with three or four representative tasks and two conditions for each as an
initial diagnostic budget, not a statistical sample-size claim. Include a known
failure, a nearby valid solution that must not be rejected, and a simple task
that must not acquire unnecessary research or planning. For material claims,
reserve a further case before tuning; an exposed case becomes regression data.

Do not put grading keys, earlier answers or evaluation-only instructions in the
executor's packet. Preserve raw outputs, artifacts and failures separately from
future inputs. Authorized work copies and frozen evidence packets serve different
purposes; use existing isolation controls without claiming a fresh context alone
isolates the filesystem.

## Inspect four distinct results

| Question | Useful observation | Invalid substitute |
| --- | --- | --- |
| Was the method selected? | Actual load/read event with the intended invocation route | The model saying it used the skill |
| Did its criteria change a decision? | Relevant action and resulting artifact against the brief | Repeated terminology or a longer report |
| Was valid nearby work preserved? | No false rejection, unsolicited effects or unnecessary process | Passing only the originally broken case |
| Was the completed task cheaper? | Total observed effort/cost through accepted delivery | Worker API price or token count alone |

Count preparation, optional advisor work, failed attempts, review, integration
and remaining user corrections. Keep wall time, billed usage and subscription
quota distinct. Record missing measurements as missing. Use deterministic checks
for objective properties and review artifacts for qualities those checks cannot
establish. A harness failure is not evidence against the method.

## Conclude within the sample

A small pilot can reveal a regression or an obviously wasteful instruction. It
cannot establish general quality, universal model portability or a savings rate.
Keep uncertainty and adverse results. Do not rerun unchanged cases until they
pass, average incompatible conditions or substitute successful discovery for
successful delivery. Remove or narrow guidance only when the protected outcome
and the legitimate control remain represented.

## Prior work and limits of transfer

[Anthropic's skill-creator](https://github.com/anthropics/skills/tree/main/skills/skill-creator)
provides concrete baseline/candidate and output-review mechanics. Borrow the
comparison structure, not an obligatory parallel campaign.
[Anthropic's evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
separates objective checks, broader grading and trajectory inspection.
[SkillsBench](https://arxiv.org/abs/2602.12670) and
[Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988) study different instruction
interventions and environments; neither supplies a measured score for Assay.
[RouteLLM](https://github.com/lm-sys/RouteLLM) motivates calibrating a routing policy
against a simple baseline, not transferring request-level economics directly to
an entire agent workflow. These sources inform method design, not results for
this candidate.
