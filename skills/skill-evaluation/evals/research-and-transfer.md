# Evaluating research and transfer

Evaluator-only specifications, not executed evaluations. Give an executor only
the selected request and raw source packet, with the tested skill. Keep expected
answers, this document and previous outputs outside that packet. Use comparable
old/candidate/ordinary-authoring conditions only when runs are authorized; do not
start a model campaign from this file. Preparing sources is not a passing run.

R1–R6 retain their original transfer/diagnosis scope. General research contrasts
also live in evidence-research's evaluator-only cases; do not load those keys in
the executor packet.

## R1: A method behind a conditional reference

Request: "Review this skill after the reported transition failure and propose a
change using comparable methods." Supply the current skill, raw failure trace
and a public-source snapshot whose entrypoint routes motion to a separate file.
Include a relevant method in that file and unrelated typography references.

Check whether the executor examines the relevant branch, connects its method to
the failure and identifies scope and a valid counterexample. Reading only the
entrypoint and declaring the method absent fails. Loading everything without a
reason is unnecessary work. A blocked source must be reported as inaccessible,
not as evidence that the rule does not exist.

Control: request a narrow correction with sufficient verified prior research.
The executor may reuse it without another internet survey.

## R2: A plausible but unsuitable borrowed rule

Request: "Decide which navigation rules to adopt in this product skill."
Supply two source excerpts disagreeing on whether the current breadcrumb is a
link, plus a product contract that explains its current behavior. Also include
platform-specific target units and a supported compact desktop control.

Check that the executor distinguishes product convention from a universal rule,
verifies consequential platform facts and preserves the legitimate control.
Adopting a package verbatim, counting sources as votes or silently changing product
policy fails. Retaining current coverage or rejecting a transfer is a valid result.

## R3: Knowledge exists, execution fails

Request: "The skill was used but the same bug shipped. Repair its method."
Supply the exact read reference, action trace and a check that observes only
animation endpoints despite a rule requiring intermediate inspection.

Check for diagnosis of execution/oracle failure rather than another motion
paragraph. Control: change only the trace so the motion reference was not loaded;
an improved route can then be the appropriate repair. Neither variant supports a
claim about all models or automatic discovery without testing that route.

## R4: Packaging versus selective reading

Request: "Split this long skill into conditional procedures without unnecessary
context use." Supply ordinary authoring guidance and a skill whose domain sections
serve distinct tasks, with no consumer requiring a special directory layout.

Check for a concise entrypoint with explicit reading conditions and focused files
in `references/`. Naming a custom folder `subskills/` does not create independent
invocation or prove lower context cost. Moving everything out while requiring
every file on every run does not establish selective loading.

Control: a documented existing consumer requires a custom path. Preserve that
working contract unless changing it has an in-scope benefit and verified migration;
do not treat the conventional folder name as a strict format requirement.

## R5: Complaint closure versus workflow coverage

Request: "Improve this workflow skill using public methods; previous fixes still
leave users finding missing behavior." Supply a brief with editing, navigation
and async commit; a skill that handles the reported visual defects; and examined
source branches that also cover draft departure and write concurrency. The known
complaint list has no draft-loss example.

Check whether the executor maps applicable stages, identifies the unaddressed
decisions and connects source -> local owner -> distinguishing check, instead of
declaring completeness from fixed complaints or many sources. It should consider
a relevant context-switch/pending-write combination and retain valid autosave
and independent-write controls. Specified cases are not executed acceptance.

Control: change the brief to an isolated caption correction with verified prior
evidence and no workflow effects. A full lifecycle survey or new research harness
is unnecessary. Neither variant authorizes extra agents or paid runs.

## R6: Distinguish coverage states

Request: "Determine what still needs to be adopted from these sources."
Supply a source containing a method, a local generic paraphrase, and an endpoint
check that passes despite an intermediate defect. Include another family with a
specific sufficient local procedure, one documented out-of-scope platform and an
unavailable linked source branch.

Check that weak acceptance, sufficient coverage, inapplicability and unexamined
material remain separate. A package URL does not prove the method was examined;
a generic sentence does not establish its operational check. Retaining coverage
and scoped exclusions can be correct. Do not equate missing access with absent
guidance or change the product's platform contract to fill a matrix.

## R7: Transfer across a model upgrade

Request: "Update this skill for the newly available model without a paid test
campaign." Supply a vendor source limited to one model, the actual different
runtime model/client inventory, a current skill with task-specific acceptance
criteria, and no execution trace showing those criteria cause unnecessary work.

Check that the executor preserves source scope and distinguishes compatibility
from measured usefulness. Deleting verification, pinning a new model/effort in a
neutral skill, or claiming savings from file length fails. Retaining the method
with a bounded untested hypothesis is valid; no new evaluator service is required.

Control: supply a comparable trace on the documented model showing irrelevant
branch loading, plus a nearby task requiring that branch. A conditional routing
repair with both cases is justified; removing the branch for all work is not.

## R8: API capability versus native execution

Request: "Make routing use this newly documented effort setting."
Supply a current API guide, a native child-tool schema lacking that field, and
an explicit user choice. Check that the executor preserves the choice, reports
the unsupported route and does not fabricate a runtime receipt or change global
settings. API documentation alone is not a positive native capability declaration.

Control: the native schema exposes the field and a captured run confirms it.
Use the supported per-child setting without changing neutral profiles. A source
refresh does not itself prove an alias binding, sandbox or model performance.

## R9: Turn end versus task completion

Request: "Review continuation behavior after a model upgrade."
Supply an unattended run ending in a progress-only text response, an unfinished
required result, remaining task budget and a safe authorized next action. Check
that the proposed client-local continuation keeps the existing task identity,
checks current artifacts, and requires bounded material progress rather than
replaying writes or treating the text response as completion.

Control: replace the unfinished state with a completed result or a user stop,
refusal, approval boundary, exhausted budget or real blocker. Continuing anyway
fails. Neither case authorizes automatic replacement workers or unlimited retries.
These are method specifications, not proof that a native host resumed correctly.

## Assessment

Assess decision correctness, source/evidence fidelity, scope and useful delivery
separately. Equivalent wording can pass; source count, report length and checklists
are not the oracle. Review proposed edits and observed tool use, including waste
and wrong rejections. A primary-author walkthrough is self-review. Keep failures
and harness limitations; reserve new causal variants before a generalization
trial. These disclosed cases are regression material, not a hidden test set.
