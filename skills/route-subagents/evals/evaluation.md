# Evaluating orchestration acceptance boundaries

Use only when revising or qualifying this skill. Give an executor one selected
case's `prompt` and `context` plus the candidate skill. Keep `rubric.json` out of
the executor context. The cases are synthetic, read-only and do not authorize
delegation, task creation, repository changes or test execution.

Compare the retained pre-edit bytes and candidate under equivalent client/model
conditions. Score decision correctness, evidence fidelity, authorized effects
and final delivery. Treat a manual walkthrough as self-review, not independent
behavioral evidence. Preserve failed or ambiguous outcomes and do not rerun an
unchanged case to select a favorable answer.

The paired controls distinguish broad from narrow acceptance, a new objective
from a repair in the same epoch, and wasteful full-suite repetition from a
material change that invalidates broader coverage. Equivalent decisions can
pass; do not grade by phrase matching.

O07-O14 additionally distinguish assignment completion from subject verdict,
deliberately matching inherited settings from explicit child choices, source ownership from runtime isolation,
and a reference to a workflow from actual delegation authority. They are
prospective decision controls; file validation is not an execution result.

O15-O17 cover economical routing for a bounded task, justified extra capability
and effort for difficult reasoning, and preserving an explicit selection under
Codex's context-fork constraints. They reject both automatic parent inheritance
and unconditional selection of the cheapest call.

## Delegation decisions and timing

O18-O33 add prospective controls for useful early delegation versus correlated
symptoms, sequential context isolation versus a trivial read, stable writer
boundaries versus shared state, changed versus unchanged readiness triggers,
material verification versus ceremonial review, using a result versus accepting
a partial return, required versus optional delegation on an unavailable host,
root-only dispatch, and immutable authorized launch inputs. These are decision
cases, not receipts for actual launches or useful parallel execution.

Run the existing hook fixture tests separately. They test the activation layer:
ordinary English/Russian requests, composition with the first workflow, explicit
catalog choices, negatives, quotations, disabled/missing skills and bounded
English hints. A passing hint test does not show that a model loaded or followed
the method. Static case/rubric validation does not execute these decision cases.

## Diagnose the responsible layer

Use an existing trace when available; do not start a paid campaign to fill a gap.
Identify the installed revision and actual invocation route before attributing
an incident to this candidate.

| Observation to inspect | Distinguishable failure |
| --- | --- |
| Native discovery/loading events or supplied skill bytes | The procedure was unavailable or never loaded; a hint alone is not loading evidence |
| The first owning plan and subsequent decisions | No useful candidate was selected despite ready independent work |
| Prerequisite changes compared with deferred decisions | A named readiness trigger was not revisited |
| Actual routing/launch response | A tool, permission or host-adapter failure rather than a planning failure |
| Worker output and integrated artifact or decision | A result was produced but not used, or partial work was reported as complete |

Missing events mean unknown execution, not proof of refusal or compliance.
Synthetic cases expose a proposed decision; actual timing and integration need
the corresponding native trace and artifacts.

## Bounded paired pilot

Use the existing execution and inspection tools on ordinary authorized work;
this addition requires no new evaluator service, telemetry store or paid runs.
Compare retained baseline bytes with the candidate under comparable model,
client, tool, permission and task conditions. Include useful delegation and a
nearby legitimate non-delegation control. Reserve a fresh private scenario before
tuning; the published O18-O33 cases are exposed regression data, not a holdout.
Keep grading keys and earlier answers out of executor inputs.

Inspect useful outcomes missed, launches made before duplicate primary work,
returns used in the intended decision, repairs, user corrections and full-chain
cost where actually observed. Count launches only as trace data, not a success
metric. Unknown subscription quota remains unknown. Keep failed attempts and
confounders; do not rerun unchanged cases for a preferred result. Report static
checks, synthetic decisions, native execution and comparative evidence as
separate levels. No behavioral improvement or savings is established merely by
shipping this method and its fixtures.
