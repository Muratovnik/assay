# Memory retrospective

Use when the review covers stored lessons, notes or memory entries rather than,
or in addition to, recent work. The goal is a store that helps the next task:
true, current, findable and free of contradictions.

## Read the store safely

Confirm the scope key returns entries you expect, then read in bounded pages.
Note the total number of entries and how many were read. A store's own
reflection, clustering or summarizing feature is optional; if it is disabled or
returns nothing, review the retrieved entries directly.

## Check each entry

| Problem | How to tell |
| --- | --- |
| Stale | It names a file, flag, version or behavior that the current source no longer has. Verify against the current files before calling it stale |
| Contradicted | Another entry, an instruction file or current behavior says the opposite |
| Duplicate | Two entries carry the same fact; keep the better-sourced one |
| Unsupported | No reason, source or incident is recorded, and none can be found |
| Not applied | Recent work shows the situation arose and the lesson was not used |
| Misplaced | It is an always-on rule that belongs in instructions, a procedure that belongs in a skill, or a mechanical fact that belongs in a check, by the owner's routing rules |
| Wrong scope | It is filed under a project or scope where it will not be found |

"Not applied" is evidence for the work review as well: reconcile it the same way
as any other candidate.

## Propose, do not curate silently

Each finding becomes a proposal with the fields in
[proposals and tracking](proposals-and-tracking.md): reinforce, edit, merge,
move or retire. Edit and retire in place rather than adding a corrected copy.
Never delete or rewrite an entry before the user decides, and keep the
superseded text recoverable when the store allows it.
