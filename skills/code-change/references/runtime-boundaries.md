# Runtime boundaries

Use when generated or dynamically compiled code, an installed API boundary or
a staged runtime operation makes source inspection or a green helper insufficient
to establish the requested result. Apply only the relevant boundaries; an ordinary
local edit does not need a new runtime harness or an exhaustive environment audit.

## Establish the inputs before effects

Identify what the actual invocation consumes: relevant source and generated
files, binary/package references, configuration and data. Inspect the runner's
resolved paths and compile inputs, including globs and ambient references, rather
than assuming its output directory determines them. Isolated output is not
isolated compile input.

Capture the relevant input state before the operation can change it, using the
existing build/evidence mechanism or a bounded snapshot when drift matters.
Recheck that input set after the run and before attributing the result to the
candidate. Relevant drift can make the run inconclusive; unrelated source edits
need not invalidate it. A snapshot taken only after failure establishes current
bytes, not which bytes the failed run consumed. Report that historical gap when
the invocation did not retain enough evidence.

## Verify the compile and API boundary

For generated or dynamically compiled code, compile the final generated bytes
through the actual compiler with the references the operation will use before
starting an expensive or stateful run. A template, handwritten approximation,
uncompiled snippet or earlier generated version cannot establish that boundary.
Use the supported build or compile-only path when available. If the runner offers
no separate compile path, establish its compile result before proceeding to later
effects; do not report an unavailable compile check as passed. Ensure the runtime
consumes the validated bytes and references; regeneration or changed references
invalidates that preflight.

Inspect the actual installed/source API boundary for signatures and semantics:
argument/return types, overloads and the relevant behavior or lifetime contract.
Names alone do not establish whether an identifier, handle or result has the
semantics the consumer needs. Compilation proves compatibility at that boundary;
it does not prove persistence, cleanup or the consumer's expected result.

## Reach the smallest supported consumer

Establish the smallest supported real consumer scenario before running a
dependent matrix. Include only the wiring, configuration and data needed to
exercise the claimed boundary. A setup or compile failure leaves later scenarios
unreached; repair or classify that prerequisite instead of interpreting every
dependent result as a separate product failure.

Check readiness of the resources the operation actually needs. An unrelated
process, residual network state or unrelated edit is not a blocker without a
causal requirement. For acquisition, cancellation, cleanup and fixture recovery,
use [external resource lifecycle](external-resource-lifecycle.md); do not invent
a second readiness or disposal policy here.

## Report the reached boundary

Record the actual invocation, relevant input identity, furthest verified stage
and outcome, using evidence from that boundary. Distinguish compilation, setup,
consumer execution and its observed result when those stages can fail separately.
An enabled default or option expresses intent; source presence or helper success
does not show that a later step ran. A successful overall command can still leave
an optional stage unexecuted.

Limit each claim to its observation: a compiler result establishes whether those
bytes compile; a supported consumer result establishes that scenario; persistence requires its
supported read/reopen boundary. Use [test writing](../../test-writing/SKILL.md)
for independent expectations and assertions. Preserve an unavailable or unreached
stage as a verification gap, without promoting it to a pass or a product defect.
