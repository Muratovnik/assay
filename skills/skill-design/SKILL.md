# Skill behavior and evaluation

Evaluate the useful difference a skill makes. Use the client's ordinary
authoring workflow for packaging and metadata; this method supplies behavioral
diagnosis and evidence criteria. Its historical name remains stable for callers.

## Locate the failure

Recover the requested outcome, current method, invocation route and relevant
prior evidence. Distinguish activation/discovery, missing or conflicting
criteria, parsing/tool failures, permission limits, reporting errors and a
disputed grading expectation. A failed run does not identify the faulty layer.
Find a check that distinguishes plausible causes before changing instructions.

Check whether the relevant rule was absent, its branch was not loaded, it was
read but not followed, or the acceptance check could pass with the defect intact.
Repair the responsible layer; another paraphrase does not fix failed execution.
For a branch that was not loaded, separate a missing catalog entry, a competing
entry that captured routing and a description that never fired; test where the
routing instruction sits as well as what it says.

For each material proposed rule identify the protected outcome and a legitimate
case an overbroad rule would reject. Vary the causal condition. A predecessor's
failure is a regression example, not a universal model limitation. Keep methods
task-based and model-neutral; client syntax belongs in conditional references,
and tested model configurations belong in evaluation records.

## Find and adapt a fitting method

For a new capability, material extension or recurring failure, identify the
decisions the skill must improve before drafting more rules. Use
[research and transfer](references/research-and-transfer.md) to connect evidence
to the local method. For unresolved substantive research use the available
[evidence-research](../evidence-research/SKILL.md) method; keep one question map
and evidence record. A typo or already justified narrow correction does not
need another survey. Existing coverage or rejecting a transfer can be correct.

When restructuring guidance, prefer the standard `references/` directory for
conditional procedures and domain detail. Keep shared rules and explicit reading
conditions in `SKILL.md`. Calling a procedure a "subskill" or moving it to a custom
folder creates no invocation or context-saving mechanism. Use a different layout
only for a concrete consumer/tooling need; preserve a working justified exception.
Check links and selective reading separately from package validity. File moves
alone do not demonstrate better behavior or lower context cost.

## Compare relevant conditions

Scale the evaluation to risk and claims. Package validation checks structure;
a manual walkthrough is self-review. Where authorized fresh runs are useful,
compare the actual prior bytes and candidate, or the same task without the
skill. For this supplement compare against ordinary authoring alone.

Keep inputs, surrounding instructions, tools, permissions and model settings
comparable. Include a failure case and a nearby valid control. Reserve a case
before tuning a material generalization; once used, it is regression evidence.
Test unintended activation separately when discovery is in scope. A model or
client change calls for rechecking relevant assumptions, not universal claims
from an earlier executor's results.

Separate decision correctness, evidence fidelity, authorized effects and actual
delivery. Inspect tool results and produced artifacts against the report.
Compare useful outcomes and remaining user corrections; word count, report size
and number of checks do not establish effectiveness. Keep failed attempts and
confounders. Do not rerun an unchanged case to obtain a preferred answer or
treat a harness failure as a subject defect.

For recurring failures, map each confirmed incident to the responsible procedure
and a distinguishing case/control; leave uncertain causes labeled as such.
Derive atomic grading requirements from the brief and verified evidence, not
only the candidate's answer. Where useful, separate finding evidence from using
already supplied evidence. Include table claims and qualifier loss during
summarization; a correct search does not prove a correct final synthesis.

## Preserve the evidence boundary

Use the intended invocation route. Explicit loading does not prove automatic
selection; a default-role run does not qualify a specialized role. Identify
skill/input bytes and keep grading keys and previous answers out of executor
packets. A fresh context is not filesystem isolation: disclose accessible keys,
missing traces and effective read/write limits. Final byte equality cannot
exclude transient writes or outside reads.

Keep raw evidence outside source and future inputs. This method authorizes no
delegation, paid campaign, installation, settings change or external mutation.
Use the existing owner tools; a failed pilot is not permission to build a new
runner, sandbox or task store.

## Decide within the evidence

Retain guidance that improves a relevant decision without rejecting valid work.
Remove duplication and superseded assumptions; moving all mandatory reading
to another file is not progressive disclosure. Report whether the result was
authored, structurally checked, discovered, behaviorally exercised or supported
by comparison. State untested hypotheses and meaningful limits. Small pilots
do not prove general quality, savings or portability across models.
