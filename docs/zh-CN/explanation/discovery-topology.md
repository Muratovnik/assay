# 为什么一份清单化的源能到达多个客户端

[English](../../explanation/discovery-topology.md) ·
[Русский](../../ru/explanation/discovery-topology.md) · **简体中文**

英文版本为准。命令输出、规则名称与配置键不作翻译。

assay 为每个技能和每个智能体配置只保留一份规范副本，并把它送达多个客户端——这些
客户端读取的目录各不相同，对配置而言文件格式也不同。本页解释这样安排的理由：技能
为何链接一次却可从两处到达、配置为何采用渲染而非链接、为何不存在 `~/.codex/skills`
投射，以及每项选择的代价。生成这套布局的命令见[安装指南](../install.md)；布局本身
见[组成方式说明](../architecture.md)。

## 问题

`catalog.toml` 是唯一的清单：它记录每项资产的归属、启用方式与各客户端的确切目标，
此外别无他物——没有模型、没有投入档位、没有运行时状态、也没有本机路径。`VERSION`
是唯一的版本标记。客户端读取的一切都应当由这两个文件生成，而不是手工编辑，因为
手工改过的清单与正确的清单毫无区别，直到它开始偏离为止。

需要从这一份源到达多个客户端的资产有两类：技能，每个受支持的客户端都能把它当作
目录读取；以及智能体配置，它在每个客户端需要不同的文件格式。二者的处理方式不同，
而这种不同正源于这一区别。

## 技能：链接一次，两处可达

技能安装一次，可从两处到达：

```text
~/.agents/skills/<name>   -> <checkout>/skills/<name>
~/.claude/skills/<name>   -> ~/.agents/skills/<name>
```

第一条链接是原生入口：它直接指向检出目录中的技能目录。第二条指向的不是技能的第二份
副本，而正是同一个原生入口。Claude 通过共享的原生根目录到达技能，而不是通过它自己
的独立投射。

理由在于：`~/.agents/skills` 并非某一个客户端的私有目录。它是多个智能体已经在读取
的通用约定——Codex 把它当作用户账号一级的技能根目录，Gemini CLI 则把它与项目中的
`.agents/skills` 视为自身根目录的别名。因此规范入口应当放在那里，而不是放进任何
单个客户端的文件夹；Claude 的根目录接入同一个入口，而不是为同一个目录另开一份独立
投射。

这样换来的是：只有一处需要核实，也只有一处需要修复。每个受支持的客户端都把技能当作
普通目录读取，因此一条链接服务所有客户端，也不存在会过期的第二份副本。代价是一重
依赖：如果 `~/.agents/skills` 下的原生入口缺失或有误，Claude 的链接就会指向空处，
尽管 Claude 自己的目录看上去毫无问题。

## 为什么不存在 `~/.codex/skills` 投射

Codex 不需要指向 `~/.codex/skills` 的链接，因为它根本不看那里。Codex 读取项目中的
`.agents/skills`（向上直至仓库根目录），以及用户账号下的 `~/.agents/skills`。它自己
的 `.system` 目录属于客户端的地盘，这里从不去管。指向 `~/.codex/skills` 的投射只会
是多出来的状态，指向一个 Codex 并不为此读取的路径：毫无所得，却让生命周期在每次
plan、安装与卸载时都要多追踪、多核实一条链接。

## 配置：渲染，而非链接

智能体配置无法用链接处理，因为 Codex 与 Claude 读取的文件格式不同：

```text
~/.codex/agents/<profile>.toml   rendered from profiles/<profile>.json
~/.claude/agents/<profile>.md    rendered from profiles/<profile>.json
```

两个目标都由同一份 JSON 源生成，每个客户端一个文件，由 `tools/assay.py render`
产出。源码校验会比对渲染字节与当前源渲染后应得的结果，因此手工改过的适配器会直接
未通过校验，而不是与它自称代表的源悄悄偏离——正是渲染让这道校验具备意义。以渲染
代替链接的代价是：现在有两个磁盘文件需要与一份源保持同步，而不是由一条链接自动
完成；源码校验就是承担这项代价的地方，而不是把它留到日后才被发现。

## 配置作为能力边界

配置是能力边界，而不是绑定了模型的角色：它不携带模型、投入档位、本机路径或运行时
状态。两个渲染出的适配器都要求客户端据此自我约束——Codex 适配器请求只读沙箱，
Claude 适配器使用 plan 模式与按能力推导出的工具列表。

只有 `evidence-reviewer` 配置获得 `Bash`，而且仅仅因为它声明的取证手段必须可执行，
否则这次审查就失去意义；它的指令依然禁止任何修改性命令，因此这项额外能力的范围是
运行一项检查，而不是改动任何东西。`official-docs-researcher` 完全不获得执行能力，
这与一个只读的研究角色相符。

这一区分有一个值得挑明的边界：适配器请求的沙箱是配置，不是保证。某次会话是否真的
执行了只读沙箱，是那次运行的属性，需要去核实，而不能从提出该请求的文件推断出来。
上一层同理——技能自动启用并不等于获得了委派给另一个智能体或修改任何东西的许可；
这条边界属于技能自身的指令与配置声明的能力，而不属于「它已被安装」这个事实。

## 本页不作的断言

组成方式说明中描述的各项校验，都不能证明某个客户端确实发现了已安装的技能，也不能
证明某次会话确实遵守了所请求的沙箱——只有在全新客户端中记录下来的一次运行才能说明
这两点。以上内容都是从仓库读出来的：它描述的是源与渲染契约，而不是任何人观察到
其正常工作的一次安装。

## 边界

本页解释的是发现拓扑，不是安装或升级步骤。创建、核实或移除这些链接与适配器的命令，
见[安装指南](../install.md)。它也不涉及受保护生命周期的预检与回滚行为，以及由
`route-subagents` 持有的委派策略——这两者都属于[组成方式说明](../architecture.md)。
